# ADR 0004：永久地址一空间一宽度

状态：已采纳

## 背景

v2 用两种方式生成永久地址，两者在实现里都出现过。

由内容派生的地址（`art_`、`evd_`）必须随内容变化而变化，所以用整个 SHA-256 摘要，64 位十六
进制。由存储分配的地址（`clm_`、`clv_`、`org_`、`top_`、`rev_`、`sgr_`、`rel_`、`pag_`）是
对象的名字，不是内容的函数，用 uuid4 的 32 位十六进制。

实施中这两者被混在了一起：`knowledge_types` 的校验 pattern 只接受 32 位，而 `evidence` 铸造
64 位，于是自己生成的证据地址无法被自己的契约引用。当时的应对是让 pattern 同时接受两种宽度，
并在流水线里加了一层截断与别名映射绕开它。这个应对留下三个问题：截断让碰撞变得可触及；同一
个宽度规则在 `webapp.py` 里被复制了第二份；两种宽度的存在使"地址是什么"没有答案。

## 决策

一个地址空间一个宽度，且由 `knowledge_types` 里的两个常量唯一定义。

- `CONTENT_ID_HEX = [0-9a-f]{64}` 用于 `art_` 与 `evd_`。内容变了地址就变，地址相同内容必然
  相同，截断会让这个性质失效。
- `STORE_ID_HEX = [0-9a-f]{32}` 用于其余全部前缀。存储分配名字，名字与内容无关。

流水线里的截断与别名映射删除，`webapp.py` 从同一组常量构造路由 pattern，不再自带一份。

`tests/test_id_width_contract.py` 断言这条不变量：两种常量各只有一处定义，铸造函数实际产出的
宽度与 pattern 一致，缩短或加长的内容地址一律不通过校验，`contract_evidence_id` 与
`evidence_alias` 的删除被守住，Web 路由不含第二份宽度定义。

## 后果

已发出的地址不需要迁移：`art_` 与 `evd_` 一直是 64 位，其余一直是 32 位，变的只是校验是否承认
它们。

新增地址前缀时必须从两个常量之一构造 pattern，并在宽度测试里登记它属于哪个空间，否则测试
失败。

引用一个地址的旧数据不会因为这条规则失效；这条规则让"地址相同则内容相同"重新成立。
